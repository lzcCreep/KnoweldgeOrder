# 知序整体架构

## 架构目标

知序采用本地优先架构：没有网络时仍能读写个人知识；登录云端后可同步业务数据；只有用户明确加入 AI 知识库的内容才建立向量索引。

## 总体组件

```text
┌─────────────────────────────────────────────┐
│ Tauri 桌面端                               │
│ React UI + 本地文件管理 + SQLite            │
└───────────────┬─────────────────────────────┘
                │ 同步业务对象 / 上传知识文件
                ▼
┌─────────────────────────────────────────────┐
│ Spring Boot 后端                            │
│ 登录、同步、文件摄取、RAG、权限、审计        │
└───────┬─────────────┬─────────────┬─────────┘
        │             │             │
        ▼             ▼             ▼
  PostgreSQL       BGE-M3        Chat Model
  云端业务数据      :8100         本地或云端
  + pgvector
  派生向量索引

外部 AI / MCP Client
  -> zhixu-mcp-server（stdio）
  -> Spring Boot 受控 API
```

浏览器开发模式可以使用 `localStorage` 或直接联调后端，但正式桌面产品以 SQLite 作为本地事实来源。

## 三层数据模型

| 层次 | 存什么 | 不存什么 | 定位 |
| --- | --- | --- | --- |
| SQLite | 笔记、标签、空间、文件元数据、本地路径、设置、同步队列 | 向量索引、大型源文件二进制 | 本机业务事实来源 |
| PostgreSQL | 云端笔记、用户、空间、文档元数据、同步版本、任务状态 | 不建议直接保存大型 PDF/DOCX 二进制 | 多端同步与后端业务库 |
| pgvector | 解析后的 chunk、1024 维向量、note/document ID、页码等 metadata | PDF 原件、完整业务对象 | 可删除、可重建的 AI 检索索引 |

SQLite 和 PostgreSQL 保存的是同一类业务对象在不同位置的副本；pgvector 不是第三份业务数据库，而是由原文派生出的索引。

## 源文件存储

用户可以在“设置 -> 文件与同步设置”指定源文件目录。导入 PDF、DOCX、图片等文件时：

```text
选择文件
  -> 可选复制到用户指定源文件目录
  -> SQLite 保存路径、哈希、大小、MIME、同步状态
  -> 用户选择上传云端时，由后端接收文件或上传到对象存储
  -> 解析文本
  -> 切块
  -> BGE-M3 向量化
  -> pgvector
```

云端源文件建议使用 MinIO/S3 等对象存储，PostgreSQL 只保存对象 key 和元数据。个人单机第一阶段可以暂时只保留本地源文件。

## 核心流程

### 本地笔记与云同步

```text
编辑笔记 -> 写 SQLite -> 记录 sync_queue
联网并点击/触发同步 -> Spring Boot -> PostgreSQL
服务端返回 revision -> 更新 SQLite 同步状态
冲突 -> 根据 UUID、revision、updated_at 进入冲突处理
```

不能上传整个 SQLite 文件并覆盖云端。必须同步业务对象或变更记录，否则多设备修改无法安全合并。

### 文件加入 AI 知识库

```text
源文件保留成功
  -> 创建 document 元数据
  -> 解析器提取正文与结构
  -> 按文档类型切块
  -> BGE-M3 生成 1024 维向量
  -> knowledge_embeddings
  -> document.index_status = ready
```

Embedding 服务失败时保留原文件和元数据，索引任务可重试。

### RAG 问答

```text
问题 -> BGE-M3 问题向量 -> pgvector Top-K
     -> 空间/用户/标签过滤 -> 可选重排
     -> Chat Model -> answer + citations[]
```

没有足够可信来源时必须拒答，不能把模型常识伪装成个人知识库内容。

### 删除语义

删除操作必须区分范围：

1. **移出 AI 知识库**：删除 pgvector chunks，保留本地和云端业务数据。
2. **删除云端副本**：软删除 PostgreSQL 业务记录，并清理向量，保留本地数据。
3. **删除本地记录**：删除 SQLite 元数据；源文件默认进入回收站或由用户二次确认。
4. **彻底删除**：本地、云端、向量、对象存储全部清理，必须强确认并写审计记录。

## 文件类型处理建议

| 类型 | 解析策略 | 切块/索引建议 |
| --- | --- | --- |
| Markdown、TXT | UTF-8 直接读取 | 按标题/段落递归切块 |
| PDF（文本型） | Apache PDFBox 或 Apache Tika | 保留页码，按段落切块 |
| PDF（扫描型） | OCR（PaddleOCR/Tesseract） | 保留页码和 OCR 置信度 |
| DOCX | Apache POI 或 Tika | 按标题、段落和表格切块 |
| HTML/网页 | Jsoup 清洗导航广告 | 保留标题、URL、抓取时间 |
| EPUB | EPUB 解析器/Tika | 按章节切块 |
| CSV/XLSX | 按表头和行组转换为结构化文本 | 小表整表，大表按行组 |
| 图片 | OCR + 图片说明 | 原图保留，索引 OCR 文本 |
| 音频/视频 | Whisper 等先转写 | 按时间段切块并保存时间码 |
| 源代码 | Tree-sitter 等语法切分 | 按函数/类，保留仓库和路径 |

第一阶段先完成 Markdown/TXT；第二阶段建议 PDFBox + POI；第三阶段再做 OCR、网页、音视频。解析器应通过统一 `DocumentParser` 接口扩展。

## 后端模块

```text
com.lzc.zhixu
├─ auth/          # 登录与会话
├─ space/         # 知识空间
├─ note/          # 云端笔记 API
├─ sync/          # SQLite <-> PostgreSQL 增量同步（待建）
├─ ingestion/     # 上传、解析、索引任务
├─ retrieval/     # 向量/混合检索（待建）
├─ chat/          # RAG 问答与引用（待建）
├─ rag/           # LangChain4j 配置和摄取骨架
├─ mcp/           # 主后端 MCP Client（待建）
└─ common/        # 错误、响应、请求 ID
```

MCP Server 是独立项目，只调用后端 API，不直接访问数据库。

## 当前与目标的差距

当前前端登录后主要直接读取 PostgreSQL；SQLite 已具备基础表和设置存储，但尚未成为完整本地事实来源，也没有同步队列。后端文档上传已保存 Markdown/TXT 原文和任务状态，但尚未真正调用 `RagPipeline` 写 pgvector。因此三层架构是确定的目标架构，尚未全部实现。

具体状态见 [项目进度.md](项目进度.md)，数据细节见 [数据与文件策略.md](数据与文件策略.md)，参数见 [参数台账.md](参数台账.md)。
